# Предметна область і межі контекстів

## Опис домену

**Сервісний центр з ремонту техніки.** Клієнти здають у ремонт смартфони, ноутбуки та іншу
техніку; приймальник оформлює замовлення, майстер проводить діагностику, складає кошторис із
запчастин і послуг та виконує ремонт, касир приймає оплату, після чого пристрій видають клієнтові.
Система веде замовлення на ремонт від приймання до видачі, підтримує каталог запчастин і послуг
з цінами та збирає відгуки клієнтів про ремонт і запчастини.

## Три обмежені контексти (Bounded Contexts)

Кожен контекст — окремий мікросервіс із власною базою даних і автономною моделлю. Спільних таблиць,
спільних схем і міжсервісних JOIN-ів немає; `FOREIGN KEY` між базами не створюються.

| № | Контекст | База даних | Технологія | За що відповідає |
|---|----------|-----------|---------------------------|------------------|
| 1 | **Repairs** (ремонти) | SQL Server, `RepairsDb` | ADO.NET + Dapper, збережувані процедури | Клієнти, замовлення на ремонт, перебіг ремонту, списання запчастин, оплата й видача |
| 2 | **Catalog** (каталог) | SQL Server, `CatalogDb` | EF Core, Code First, Fluent API, міграції | Довідник запчастин і послуг: назви, ціни, бренди, категорії, описи |
| 3 | **Reviews** (відгуки) | MongoDB, `ReviewsDb` | MongoDB Driver, Clean Architecture, CQRS | Відгуки про ремонт і позиції каталогу, коментарі, обговорення, рейтинги |

### Чому саме така технологія

- **Repairs → реляційна БД і процедури.** Ремонт — транзакційний процес зі строгим життєвим циклом:
  зміна статусу, запис в історію та списання запчастин мають виконуватися як одне ціле. Тут потрібні
  транзакції, блокування, обмеження цілісності й збережувані процедури.
- **Catalog → реляційна БД і EF Core.** Каталог — це багато пов'язаних сутностей з усіма типами
  зв'язків (1:1, 1:N, M:N), довідникові дані та схема, що еволюціонує, — типовий сценарій для
  Code First із Fluent API та міграціями.
- **Reviews → MongoDB.** Відгуки мають змінну структуру (відгук про ремонт і відгук про запчастину
  описуються різними полями), вкладені коментарі та читаються цілим документом — це документний агрегат.

## Сутності: кожна належить рівно одному контексту

| Контекст-власник | Сутності | Де фізично зберігаються |
|------------------|----------|-------------------------|
| **Repairs** | `Customer` (клієнт) | `RepairsDb.dbo.Customers` |
| | `RepairOrder` (замовлення на ремонт) | `RepairsDb.dbo.RepairOrders` |
| | `RepairOrderDetails` (пристрій і несправність) | `RepairsDb.dbo.RepairOrderDetails` |
| | `RepairOrderItem` (позиція кошторису) | `RepairsDb.dbo.RepairOrderItems` |
| | `RepairOrderStatusHistory` (журнал статусів) | `RepairsDb.dbo.RepairOrderStatusHistory` |
| | Залишок запчастини на складі (`Stock`) | поле `RepairsDb.dbo.CatalogItems.Stock` |
| **Catalog** | `Brand` (бренд) | `CatalogDb.dbo.Brands` |
| | `Category` (категорія) | `CatalogDb.dbo.Categories` |
| | `CatalogItem` (запчастина або послуга) | `CatalogDb.dbo.CatalogItems` |
| | `CatalogItemDetail` (розширений опис) | `CatalogDb.dbo.CatalogItemDetails` |
| | `CatalogItemCategory` (належність до категорії) | `CatalogDb.dbo.CatalogItemCategories` |
| **Reviews** | `Review` (відгук) з вбудованими `Comment`, `StaffReply` | колекція `reviews` |
| | `Discussion` (тема обговорення) | колекція `discussions` |
| | `DiscussionMessage` (повідомлення) | колекція `discussionMessages` |
| | `ItemRatingSummary` (зведений рейтинг) | колекція `itemRatingSummaries` |

### Сутності, потрібні кільком контекстам

Якщо сутність потрібна двом контекстам, один із них — власник, а інший зберігає лише її
ідентифікатор і, за потреби, копію окремих полів (деталі — у [таблиці політики дублювання](duplication-policy.md)).

| Сутність | Власник | Хто ще використовує | Що зберігає не-власник |
|----------|---------|---------------------|------------------------|
| `CatalogItem` | Catalog | Repairs | `RepairsDb.dbo.CatalogItems` — локальна копія (той самий `Id`, `Name`, `ItemType`, `Price`) без FK на `CatalogDb`; знімки `ItemName`, `UnitPrice` у позиціях замовлення |
| `CatalogItem` | Catalog | Reviews | поле `catalogItemId` і копія назви `itemName` у документах |
| `Customer` | Repairs | Reviews | поле `author.customerId` і копія імені `author.displayName` |
| `RepairOrder` | Repairs | Reviews | поле `repairOrderId` і знімок пристрою `device` |

Таблиця `RepairsDb.dbo.CatalogItems` не робить контекст Repairs співвласником позиції каталогу:
це копія для читання, яку Repairs сам не редагує (окрім власного поля `Stock`).

## Агрегати та життєвий цикл даних

Агрегат — коренева сутність разом з об'єктами, що не існують без неї та змінюються лише через неї.

### Repairs

| Агрегат | Корінь | Що входить | Життєвий цикл |
|---------|--------|-----------|---------------|
| **Замовлення на ремонт** | `RepairOrders` | `RepairOrderDetails` (1:1), `RepairOrderItems`, `RepairOrderStatusHistory` | Створюється під час приймання (`usp_CreateRepairOrder`) одразу з деталями та першим записом історії. Змінюється лише через процедури: позиції — `usp_AddRepairOrderItem`, статус — `usp_ChangeRepairOrderStatus`. Після видачі або скасування архівується м'яким видаленням. Дочірні рядки видаляються каскадно разом із коренем. |
| **Клієнт** | `Customers` | — | Живе незалежно від замовлень; фізично не видаляється, якщо має ремонти (FK без каскаду), лише `IsDeleted = 1`. |
| **Складська позиція** | `CatalogItems` | — | Рядок з'являється й оновлюється подіями з Каталогу; сам Repairs змінює тільки `Stock`. |

Життєвий цикл замовлення:

```text
Accepted -> Diagnosed -> Approved -> InRepair -> Ready -> Paid -> Issued
    \____________\___________\
                  \-> Cancelled   (лише до початку ремонту)
```

### Catalog

| Агрегат | Корінь | Що входить | Життєвий цикл |
|---------|--------|-----------|---------------|
| **Позиція каталогу** | `CatalogItems` | `CatalogItemDetails` (1:1), зв'язки `CatalogItemCategories` | Створюється менеджером каталогу; ціну й назву змінює лише Catalog і сповіщає інші контексти подією. Знімається з продажу через `IsActive = 0` або `IsDeleted = 1`. |
| **Бренд** | `Brands` | — | Довідник; бренд із позиціями видалити не можна. |
| **Категорія** | `Categories` | підкатегорії через `ParentCategoryId` | Довідник з ієрархією; категорію з підкатегоріями видалити не можна. |

### Reviews

| Агрегат | Корінь | Що входить | Життєвий цикл |
|---------|--------|-----------|---------------|
| **Відгук** | документ `reviews` | вбудовані `author`, `comments[]`, `staffReply`, `usedItems[]`, `device` | Створюється клієнтом після ремонту або покупки; читається й зберігається цілим документом. Останні коментарі — усередині документа (не більше 20). |
| **Обговорення** | документ `discussions` | вбудований `lastMessage` | Відкривається з відгуку, закривається персоналом. Повідомлень необмежено багато, тому вони — окремі документи `discussionMessages` з посиланням на обговорення. |
| **Зведений рейтинг** | документ `itemRatingSummaries` | вбудована гістограма оцінок | Похідні дані: перераховується агрегацією з відгуків. |

## Ключі та конкурентність: обґрунтування

- **`BIGINT IDENTITY`** для сутностей, які створює одне джерело (свій сервіс): послідовні значення не
  фрагментують кластерний індекс, ключ займає 8 байт проти 16 у GUID. GUID був би доречний, якби
  ідентифікатори генерувалися в кількох місцях незалежно (офлайн-клієнти, кілька інстансів без спільної БД).
- **`RepairsDb.dbo.CatalogItems.Id` без `IDENTITY`**: значення не генерується, а приходить із Каталогу.
- **`ObjectId`** у MongoDB генерується на боці застосунку без звернення до бази; для
  `itemRatingSummaries` ключем є сам `catalogItemId` — один документ на позицію.
- **Оптимістична конкурентність**: `ROWVERSION` у таблицях, де один рядок можуть одночасно змінювати
  двоє користувачів (`Customers`, `RepairOrders`, `RepairOrderDetails`, `CatalogItems` в обох базах);
  у MongoDB — ціле поле `version`. У таблицях, де рядки лише додаються (`RepairOrderStatusHistory`),
  він не потрібен. Песимістичне блокування (`UPDLOCK`) використано тільки всередині коротких
  транзакцій процедур, де перевірка й зміна мають бути неподільними.
